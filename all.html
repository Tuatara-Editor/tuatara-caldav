caldav Manual

for Tuatara 0.90.39 and later, every chapter on one page

This manual is written with modal editing on, first and foremost. Where a command also has a key that works with modal editing off, it is given as well, as the non-modal key.

What caldav is

Tuatara's agenda shared with other calendars through a CalDAV server.

caldav keeps the calendars of a CalDAV server in an Org file and syncs them in both directions. What you add or change in an entry goes to the server, and what changed on the server comes into the entry. GNOME Calendar, Thunderbird and phones that use the same server see the same events.

Two servers are described in this manual:

  • Radicale, which Fedora, Debian, Ubuntu and Arch package. It runs on a computer of your own.
  • EteSync, through its local bridge, etesync-dav, which keeps the calendars encrypted end to end.

Any other CalDAV server works the same way. Chapter 2 sets up the two above, chapter 3 gives Tuatara the account, and chapter 4 syncs.

1.1 The programs it uses

The package needs two small programs. curl makes every request to the server. secret-tool keeps the server's password in the desktop's keyring. Check them in a terminal:

curl --version
secret-tool --help

The README says how to install them.

1.2 The keys

In Org files and in the agenda, the keys are under C-c s, which Tuatara labels calendars in its key help.

  • C-c s s (caldav-sync) syncs now.
  • C-c s n (caldav-event-new) writes a new event.
  • C-c s l (caldav-calendars) lists the server's calendars.
  • C-c s d (caldav-deleted) deletes on the server what you deleted here.
  • C-c s i (caldav-import) reads a calendar file (.ics).
  • C-c s e (caldav-export) writes entries as a calendar file. It is bound in Org files only.

Every command also runs with M-x in any buffer. Chapter 4 says what each does.

1.3 Where the calendars are kept

The calendars are in one Org file, with a heading for each calendar and its events under it. The setting *caldav-file* names the file. Its default, "agenda-caldav.org", is a file beside the first of your agenda files. The agenda reads it whether or not *org-agenda-files* names it.

(setf *caldav-file* "agenda-caldav.org")        ; the default
(setf *caldav-file* "~/Documents/agenda.org")   ; among your own entries

A name alone is a file beside the first agenda file. A path is that file.

Only the calendars' file is synced. Your own agenda file and notes are never read for it and never changed. When you set *caldav-file* to one of your agenda files, the calendars are headings among your own, and only what is under a calendar's heading (the one with a CALENDAR property) is synced. The rest of the file is left as it is.

1.4 What is kept apart from the file

What each calendar last agreed with its server is kept in ~/.local/state/tuatara/calendars/, never in the Org file. It holds the sync token and a copy of each event. The copy gives what an entry does not say: the attendees, alarms and properties that other programs keep are sent back as they were.

1.5 Subscriptions

A subscription is a calendar file at an address, public holidays for example. It is read into the agenda and never sent back. Each one is fetched at every sync and written as an Org file of its own in the cache, which the agenda reads among its files.

(setf *caldav-subscriptions*
      '((:name "Holidays" :url "https://example.org/holidays.ics")))

:name is what its heading is called and :url is its address, which must be https.

A calendar server

Setting up EteSync or Radicale for caldav to talk to.

You need a calendar server, the package in Tuatara, and the server's password in your desktop's keyring. Pick one of two ways to have a server:

  • A. EteSync, if you have an EteSync account. Your calendars stay encrypted end to end. A small program on your computer, etesync-dav, lets Tuatara, Thunderbird and GNOME Calendar talk to them.
  • B. Your own Radicale, free, on a computer of yours that is on. You reach it from your laptop and phone over Tailscale, a private network between your own devices. Nothing is open to the internet.

The examples write you for your user name, EteSync for an account's name and home-server for the computer that keeps the calendars. Write your own.

2.1 A. EteSync: run etesync-dav

  1. Download etesync-dav for Linux from its releases page, https://github.com/etesync/etesync-dav/releases, into ~/.local/bin/, and make it runnable:

       chmod +x ~/.local/bin/etesync-dav

    pipx install etesync-dav works too. On the newest Python versions one of its parts may not build, and the download always works.

  2. Start it and add your account:

       etesync-dav manage add you      # asks your EteSync password once
   etesync-dav manage get you      # shows the password for programs here
   etesync-dav                     # keep this running

    The password manage get shows is not your EteSync password. etesync-dav made it for programs on this computer, and it is the one Tuatara needs. Its page, http://localhost:37358/, shows the same with Copy Password.

  3. Have it start with your computer. Add etesync-dav to your desktop's startup applications (GNOME: the Tweaks app, Startup Applications; KDE: System Settings, Autostart).

etesync-dav answers on http://localhost:37358/ and only to this computer, which is why Tuatara may use plain http for it.

2.2 B. Your own Radicale, reached over Tailscale

Do this on the computer that keeps your calendars: a desktop that is on, a small home server or a Raspberry Pi. It is called home-server here.

  1. Install Radicale and the password tools:

    SystemCommand
    Fedorasudo dnf install radicale httpd-tools python3-bcrypt
    Debian, Ubuntusudo apt install radicale apache2-utils python3-bcrypt
    Arch, Omarchysudo pacman -S radicale apache python-bcrypt

  2. Make your user and its password. Use a long one of its own, not used anywhere else. -B keeps it as a bcrypt hash, never as it is:

       sudo htpasswd -B -c /etc/radicale/users you

  3. Tell Radicale to listen to this computer alone and to ask for that password. Edit /etc/radicale/config so these sections say:

       [server]
   hosts = localhost:5232

   [auth]
   type = htpasswd
   htpasswd_filename = /etc/radicale/users
   htpasswd_encryption = autodetect

   [rights]
   type = owner_only

    owner_only lets each user see their own calendars alone.

  4. Start it, now and at every start:

       sudo systemctl enable --now radicale

    Open http://localhost:5232/ on that computer, log in, and make a calendar (Create new addressbook or calendar). Tuatara syncs the calendars that are there. It never makes one.

  5. Install Tailscale on this computer and on every device that should see your calendars: https://tailscale.com/download. Sign in to the same account on each, and on Linux run:

       sudo tailscale up
  6. Turn on HTTPS for your tailnet, once. In the Tailscale admin page, https://login.tailscale.com/admin/dns, enable MagicDNS and HTTPS Certificates.

  7. Give Radicale an https address on your tailnet, on home-server:

       sudo tailscale serve --bg 5232
   tailscale serve status

    The status shows its address, such as https://home-server.tail1234.ts.net/. Only your own devices, signed in to your tailnet, can reach it, with a real certificate. Nothing is open to the internet. Never use tailscale funnel, which opens it to everyone, and never forward a port on your router for it.

On home-server itself Tuatara may use http://localhost:5232/. On your other computers it uses the https://...ts.net/ address.

2.3 The same calendars elsewhere

  • Thunderbird: File, New, Calendar, On the Network. Give the user name and the address, then Find Calendars.
  • GNOME Calendar: Settings, Online Accounts, Calendar, Contacts and Files (WebDAV). Give the address, user and password.
  • Android: the Tailscale app, then DAVx5 (Login with URL and user name), and any calendar app.
  • iPhone and iPad: the Tailscale app, then Settings, Calendar, Accounts, Add Account, Other, Add CalDAV Account.
  • Phones with EteSync: the EteSync app itself. etesync-dav is for computers.

Accounts and passwords

Telling Tuatara which server to sync with and where its password is kept.

3.1 The password in the keyring

On each computer Tuatara syncs from, store the password in the desktop's keyring. Never write it in the init file.

secret-tool store --label="Tuatara calendars" service tuatara-caldav user you

It asks for the password. For EteSync give the one etesync-dav manage get showed. For Radicale give the one you gave htpasswd.

3.2 The password in a GnuPG file

Instead of the keyring, the password can be kept in a file encrypted with GnuPG and given by a command, as mbsync's PassCmd gives one:

printf '%s\n' 'THE-PASSWORD' | gpg --symmetric --output ~/.etesync-pass.gpg
chmod 600 ~/.etesync-pass.gpg

The first command asks for a passphrase for the file. Clear your shell's history of that line afterwards, or type the password into a file and encrypt the file, then delete it. Then give the account a :password-command:

'((:name "EteSync" :url "http://localhost:37358/" :user "you"
   :password-command
   "gpg --quiet --for-your-eyes-only --no-tty --decrypt ~/.etesync-pass.gpg"))

At each sync Tuatara runs the command, with no shell. A word beginning with ~/ is a path in your home directory. The first line the command prints is the password. gpg-agent asks for the file's passphrase in a window of its own and remembers it for a while: 10 minutes as standard, each use counting again, so syncing every minute keeps it remembered up to gpg-agent's limit, two hours as standard. Then it asks again.

The password is never written anywhere. It goes from gpg to curl through pipes, and Tuatara's own copies of it are wiped from memory once used. When the command fails, Tuatara says so, and never says what the command printed.

3.3 If the password was stored for calendar-sync

Before Tuatara 0.90.13 the package was called calendar-sync, and its password was kept under the service tuatara-calendar-sync. Copy it to the new name once, on each computer that has it, you being the account's :user. The password is not shown:

secret-tool lookup service tuatara-calendar-sync user you | secret-tool store --label="Tuatara calendars" service tuatara-caldav user you

Once C-c s l (caldav-calendars) lists the account's calendars, Tuatara has found the password under its new name, and the old entry can go:

secret-tool clear service tuatara-calendar-sync user you

3.4 Loading the package with an account

Open your init file, add this with one of the two accounts (delete the other's lines, or start them with ;;, which Tuatara reads past), and save:

(load-package "caldav" :source "https://github.com/Tuatara-Editor/tuatara-caldav"
              :version "latest"
  :config
  (setf *caldav-accounts*
        ;; A. EteSync
        '((:name "EteSync" :url "http://localhost:37358/" :user "you"))
        ;; B. Radicale over Tailscale
        ;; (on home-server itself: "http://localhost:5232/")
        ;; '((:name "Home" :url "https://home-server.tail1234.ts.net/"
        ;;    :user "you"))
        ))

Start Tuatara again. It asks once whether to load the package.

3.5 The accounts setting

*caldav-accounts* is a list of accounts. Each is a list of keywords and values.

  • :name is what its calendars' headings are named after.
  • :url is the server's address: https, or http to this machine alone.
  • :user is the name it signs in with.
  • :calendars names those of its calendars to sync. Every calendar is synced when it is not given. C-c s l lists the names Tuatara finds.
  • :password-command is a command that gives the password, run without a shell.
'((:name "EteSync" :url "http://localhost:37358/" :user "you"
   :calendars ("Personal" "Family")))

The address is the server's own. The calendars are found from it as CalDAV says (the principal, then its calendar home). Each calendar is a heading of its own in the calendars' file, its address in the CALENDAR property.

Syncing

When calendars are synced, and what each command does.

4.1 Automatic syncing

The calendars sync on their own, a few seconds after Tuatara starts and then every minute, in the background. Nothing is said unless something changed or failed. A failure is told once, not again every minute while it lasts.

A sync that finds nothing changed costs one request for each account's calendars, and reads and writes nothing on your drive.

*caldav-minutes* sets how often. Give minutes, or words such as "30m" or "1h". It is never more often than once a minute. Give nil, or 0 or less, to sync only when asked.

(setf *caldav-minutes* 5)

4.2 Syncing at once

C-c s s (caldav-sync) syncs every account's calendars and fetches the subscriptions, in the background. The first sync writes agenda-caldav.org beside your agenda file, a heading for each calendar, and the agenda shows its events. In an Org file or the agenda C-c s s works. M-x caldav-sync works anywhere.

A sync sends what you changed in an entry and fetches what changed on the server since the last sync, then writes it into its entry. Only the lines that differ are changed, as one step to undo, and the file is saved. Your own lines in an entry (notes, checkboxes, clocks, properties of your own) are kept when the server's version is written.

After each sync Tuatara says what it did in one line, and what failed after failed:. C-h e shows the messages again. A failed sync is also told as a notification, on the desktop and in *Notifications* (C-h N).

4.3 What happens to an entry

  • New entries under a calendar's heading become events on its server. Their UID is written into them.
  • Deleted on the server: the entry is deleted too. One that holds lines of yours (notes, checkboxes, clocks, properties of your own) stays. It is tagged removed and no longer synced, and its times are made inactive ([2026-11-05 Thu]) so the agenda shows it no more. Delete it when you are done with it.
  • Deleted here: nothing happens on the server until C-c s d asks you. When you answer no, the entries are put back.
  • Cancelled here (C-c C-x C, keyword CANCELLED or CANCELED): its event is deleted on the server at the next sync, so it leaves your other devices. The entry stays, tagged removed and no longer synced. The agenda still shows it, cancelled. An entry cancelled before it was ever sent is not sent.
  • Changed on both sides: the server's version stands in the entry, and yours is kept beside it, tagged conflict and no longer synced. Copy what you want from it and delete it.

4.4 The other commands

C-c s l (caldav-calendars) says the calendars each account has and which of them are synced. It only asks the server, so it shows that Tuatara reaches it. It works when nothing else does.

C-c s d (caldav-deleted) deletes on the server the events whose entries you deleted, after asking. Answer no and the entries are put back.

C-c s i (caldav-import) reads a calendar file (.ics) under one of your calendars, or under a heading of its own.

C-c s e (caldav-export) writes the entry at point and those under it, or the entries selected, as a calendar file. It is bound in Org files only.

4.5 A new event

C-c s n (caldav-event-new, or M-x caldav-event-new anywhere) asks which calendar when you have more than one, then the event's title, its place (RET for none) and its time in the calendar. A form opens with the cursor between the description block's two lines. Write the description there, or nothing.

  • C-c C-c files the event under the calendar's heading, and the server gets it at the next sync.
  • C-c C-w files it under another heading instead.
  • C-c C-k throws it away.

The #+name: description line marks the block as the description, so leave it as it is. A location or description left blank is none, and nothing is sent for it.

Events as Org entries

How an event or task of a calendar is written as an Org heading.

Each event or task is one heading. Its UID is kept in the UID property.

  • SUMMARY is the heading.
  • DTSTART, DTEND and DURATION are an active timestamp on your computer's clock, such as <2026-11-03 Tue 09:00-10:00>, a range for several days.
  • A weekly, monthly or yearly rule that Org's repeater can say is the repeater: +1w, +2w, +1m, +1y.
  • A rule such as the second Tuesday, Mondays and Fridays, every other week on two days, three times only, or until a day is a date by rule, as the repeat menu of the date prompt writes it (C-c C-s, then C-r): <%%(and (diary-block 11 10 2026 1 12 2027) (diary-float t 2 2)) 18:00-20:00>.
  • EXDATE, or a time changed alone, is a note in the logbook of the time cancelled or moved. Cancelling one time (C-c C-x C) and scheduling one time elsewhere (C-c C-s) write the same notes.
  • A rule Org cannot say, such as the last weekday of a month, is each time written out within the days kept (a year back, two ahead, at most 500 times), with the rule in the RRULE property. These times belong to the calendar and are never sent back.
  • A task's DUE, DTSTART and COMPLETED are TODO with DEADLINE, SCHEDULED, DONE and CLOSED.
  • LOCATION is the LOCATION property.
  • CATEGORIES are tags. Public Holiday is Public_Holiday.
  • STATUS:CANCELLED is the tag cancelled.
  • DESCRIPTION is an example block named description.

Read back, an entry gives the same properties. Several timestamps in one entry are an event each, the UID of the second and later ones followed by their day. Everything else the calendar keeps of an event (attendees, alarms, its own properties) is kept as it was. Times the entry still says as the calendar did are sent as the calendar wrote them.

Words from a calendar stay words. A title stays on one line, a description stays inside its block, and neither can become a heading, a link, a timestamp, a clock or a note the agenda reads.

5.1 Calendar files

A calendar file is read into its components (a calendar, its events, tasks and time zones) and their properties, kept as written, so a file read and written again loses nothing. Lines are written folded at 75 octets, never inside a character.

  • Values are read when asked for: text with its escapes, dates and times (floating, UTC, or in a named time zone), durations, offsets and rules of recurrence.
  • A time zone a file names is found in the file's own definition first, then among the system's (/usr/share/zoneinfo), the name checked to be a zone's name and nothing more. One is written for a zone by its yearly rule.
  • Recurrences cover every part of a rule of recurrence, extra dates, dates taken out, and occurrences changed one by one. They are expanded only within the days asked for, and are checked against the examples in RFC 5545 itself.

Safety, limits and what to do when it fails

What the package never does, what it refuses, and how to find a fault.

6.1 Why it is safe

  • The password is kept by the desktop's keyring, or encrypted by GnuPG. It is given to curl on its standard input, never on its command line or in a file, and Tuatara's copies are wiped from memory once used. It is sent only to the server's own address, whatever the server's answers name.
  • Every request goes through curl. The address is https, or http to this machine alone (etesync-dav). A redirect elsewhere is not followed, and at most five redirects are taken.
  • Tuatara talks https to every other computer. With Tailscale the calendars travel inside your own private, encrypted network as well.
  • Radicale listens to its own computer alone, Tailscale's https address is for your devices alone, and each user sees their own calendars alone.
  • Nothing a server sends is ever run. Calendar files are read as data, and their words are written into Org as words.

6.2 Limits

A calendar file comes from elsewhere and is never trusted.

  • A request is bounded at 32 MB and 60 seconds.
  • The reader refuses a calendar file larger than 16 MB, or with components nested more than 20 deep.
  • No more than 10,000 occurrences of one event are worked out at once.

6.3 When nothing is said

If there are no messages at all, the sync was not started. C-c s s works in an Org file or the agenda only, and M-x caldav-sync works anywhere. Start with C-c s l, which only asks the server for its calendars and says what it found, or why it could not.

6.4 Messages

After a failed sync the message names the account or calendar and says why, in curl's own words when the server could not be reached (Could not connect to server, Could not resolve host, Operation timed out).

  • No password for ... in the keyring: the keyring step of chapter 3 was not done for that user name, or was done for a different one than the init file says.
  • refused the name and password: the password in the keyring is not the server's. For EteSync it is the manage get one, not your EteSync one.
  • not reached: Could not connect to server: the server is not running (etesync-dav, or sudo systemctl status radicale), or Tailscale is off on this device (tailscale status).
  • is not https, nor on this machine: an http:// address of another computer. Use its https://...ts.net/ address (chapter 2, B, step 7).
  • says no calendars: make a calendar first, in chapter 2 B step 4 or in EteSync.

Every command and setting

Each command and setting of caldav, to look one up by name.

The tables are made from the program each time this manual is made, so they never list a command or setting that caldav does not have. The first table has four columns. The first two are keys: the modal keys, which work only with modal editing on, and the non-modal keys, which work with it off too. A command with no key says M-x and its name in the second column, because you can only run it by its name. The third column is the name of the command and the fourth says what it does.

To run a command by its name, press M-x, type a few letters of the name and press RET. To find a command from within the editor, press C-h f. To find the command that a key runs, press C-h k and then the key. The editor's own settings and commands are in chapters 21 and 22 of its manual.
